# ComfyUI Tag Template Manager — Phase 1 Core 設計書

作成日：2026-11-12  
位置づけ：[全体設計 v1.0](ComfyUI_Tag_Template_Manager_Design_v1.md) の第1段階を具体化した実装用設計。以下の細則はこの段階の提案であり、全体設計で未確定の事項を補う。

## 1. 目的と範囲

ComfyUI の画面やサーバーを起動せずにテストできる Python の基盤を作る。テンプレートの検証、個別 JSON ファイルへの保存と読み込み、選択状態からの Positive / Negative の生成を扱う。データ破損や誤った選択を空の結果に置き換えず、呼び出し側に原因を渡す。

対象は `services/` と単体テスト。Python 3.10 以上の標準ライブラリを使用し、現在のポータブル版 Python 3.13 で実行する。

対象外は ComfyUI ノードと UI、HTTP API、ユーザーディレクトリの ComfyUI への接続、ワークフロー保存、実行キャッシュ、Snapshot、インポート／エクスポート画面と破損復旧 UI。Core のファイル保存はこれらの後続機能の基盤となるが、MVP 全体の完成を意味しない。

## 2. 構成方針

| 方式 | 特徴 | 判断 |
| --- | --- | --- |
| ComfyUI に依存しないサービス層 | 入出力を分離して単体テストでき、後からノードと API の両方から使える | 採用 |
| ノードや HTTP ハンドラーに直接実装 | 初期ファイル数は少ないが、画面やサーバーに依存し検証しにくい | 採用しない |

`services/schema.py` は検証とモデル、`services/template_store.py` は永続化、`services/prompt_builder.py` は選択・結合を担当する。ComfyUI へのパス解決や例外の UI 表示は後続段階の責務とする。Core は保存先ディレクトリを引数で受け取り、テストでは一時ディレクトリを使う。

## 3. データと検証

全体設計 §6 の JSON をバージョン 1 の形式とする。配列順をブロックとプリセットの表示順として保持し、タグ本文は保存時に書き換えない。ID は表示名と独立し、名前の変更で変わらない。

| 対象 | 検証規則 |
| --- | --- |
| Template | `schema_version` は整数 `1`、`id` と `name` は必須、`category` と `description` は文字列、`blocks` と `presets` は配列。空の配列は許可する |
| Block | `id`、`name`、`channel`、`default_enabled`、`exclusive_group`、`tags` を必須とする。`channel` は `positive` または `negative`、`default_enabled` は真偽値、`exclusive_group` は null または空でない文字列、`tags` は空文字列を含む文字列 |
| Preset | `id`、`name`、`enabled_block_ids` を必須とし、最後の項目は重複しない既存 Block ID の配列とする。空配列はすべて無効を表す |

- `id` はファイル名にも使用するため、Template・Block・Preset とも英数字、`_`、`-` のみ、1〜128文字とする。表示名は空白のみを不可とし、日本語を含む文字列を許可する。ID は種類ごとに一意とする。
- `category` と `description` は空文字列を許可する。型を暗黙変換せず、未知のフィールドも拒否する。将来の形式変更は `schema_version` により明示的に扱い、未知のバージョンを拒否する。
- 同じ `exclusive_group` で、既定状態または各プリセットに複数の有効ブロックがあるデータを拒否する。ゼロ個は許可する。グループはチャンネルに関係なくテンプレート内で共有する。
- JSON の同名キーの重複、必須項目の欠落、不正な型、参照先の不存在は検証エラーにする。エラーには対象項目のパスと理由を含める。

## 4. 選択とプロンプト生成

選択状態はテンプレートのマスターとは別の値として扱う。初期状態はブロックの `default_enabled` を使う。プリセット適用は、その `enabled_block_ids` に含まれるものだけを有効にする完全な置き換えとする。その後の個別変更では、同じ排他グループ内の別ブロックを有効にすると、それまで有効だったブロックを無効にする。無効化は他の状態を変更しない。

保存済みの選択を使用する入口は、Block ID と真偽値の対応を受け取る。完全な状態として扱い、未知 ID、欠落 ID、型不正、排他違反を拒否する。将来の Live 更新でブロックが追加・削除された場合の復元・移行方法は Nodes / Stability で決める。Core が黙って補完・削除することはしない。

結合処理は、呼び出し側がポート順に並べたテンプレートとそれぞれの選択状態、および自由入力を受け取る。テンプレート順、各テンプレートのブロック配列順、最後に自由入力の順に、チャンネルごとに処理する。

1. 無効ブロックを除き、各断片の両端の空白と区切りカンマを除去する。結果が空なら無視する。断片内部はそのまま保持する。
2. 重複除去 OFF では残った断片を `, ` で連結する。Positive と Negative は独立して処理する。
3. 重複除去 ON では、断片全体が英数字、空白、アンダースコア、ハイフン、カンマだけからなる場合に限り、カンマで平文タグに分ける。各タグの両端の空白を除いた完全一致で、チャンネルごとに最初の出現を残す。大文字小文字は区別する。
4. 括弧、角括弧、コロン、バックスラッシュ、改行以外の制御文字、または上記の安全な文字以外を含む断片は分割・重複除去せず、そのまま連結する。改行も安全な文字には含めない。`BREAK` は単独でも特殊な区切りとして扱い、それを含む断片は分割・重複除去しない。

安全性を優先するため、複雑な断片と平文断片の間の重複や、日本語タグを含む断片内の重複は除去しない。たとえば `cat, cat` は ON で `cat`、`(cat, dog), cat` はそのまま残る。括弧の意味解析やタグの追加はしない。プレビューと実行出力を同じ処理にする統合は Nodes 以降で行う。

## 5. 保存とエラー

- ストアの公開操作は一覧、ID 指定の読み込み、新規作成、既存更新、削除とする。作成と更新を分け、新規作成は同一 ID があれば失敗し、更新と削除は対象がなければ失敗する。複製は新しい ID での作成として後続の呼び出し側が扱う。
- ファイルは指定ルート直下の `<template-id>.json`、UTF-8 とする。ID を検証してからパスを構築し、JSON 内 ID とファイル名が異なる場合はエラーとする。利用者が任意のパスを渡す操作は提供しない。
- 保存前に全体を検証し、同じディレクトリの一時ファイルに書き込んでから置換する。失敗時は一時ファイルを片付け、既存ファイルを維持する。新規作成の衝突は並行実行でも上書きにならないよう排他的に確保する。複数プロセスによる既存データの同時更新検出はこの段階の対象外。
- 一覧は ID 順とし、破損ファイルを黙って除外しない。読み込み・一覧での JSON 不正、検証エラー、権限エラー、ID 不一致は、ファイルまたは ID と原因を含む例外として返す。存在しないディレクトリはストア初期化時に作成する。
- 外部から指定されたシンボリックリンク等を通じてルート外を操作しないよう、対象が通常ファイルであることと保存先の境界を確認する。削除の確認ダイアログやバックアップは後続の API / UI で扱う。

## 6. サービス間の契約

具体的なクラス名や型名は実装時に決めるが、次の性質を守る。

- 検証は外部データから安全なモデルを作る入口を一つ用意し、保存前・読み込み後とも同じ規則を通す。呼び出し元の辞書やマスターを選択・結合処理が変更しない。
- ストアは ComfyUI を import しない。読み書きの失敗、未存在、ID 衝突、検証失敗を呼び出し側で区別できる例外として公開する。
- 選択と結合はファイルや時刻、グローバル状態に依存しない。同じ入力から同じ出力を返す。Positive / Negative は別々の文字列として返す。
- ノード接続用 `TAG_BUNDLE`、実行キャッシュのリビジョン、および実際の ComfyUI ユーザーディレクトリ解決は後続段階で、対象バージョンの API を確認して設計する。

## 7. テストと完了条件

`unittest` と `tempfile` を使用し、少なくとも次を検証する。

- 全体設計の JSON 例の読み込み、保存・再読み込みでの順序と日本語・タグ本文の保持。
- 必須項目、型、未知フィールド・バージョン、重複 JSON キーと各 ID、参照切れ、既定値・プリセットの排他違反、パストラバーサルの拒否。
- 作成・更新・一覧・削除、ID 衝突・未存在・ファイル名不一致・壊れた JSON・I/O エラー。保存失敗時に既存データが残ること。
- 既定値、プリセット、個別切替、排他と選択の独立性。不正な選択の拒否。
- 複数テンプレートと自由入力の順序、チャンネル分離、空要素、区切りの整理、重複除去の ON / OFF、複雑な構文と `BREAK` の保護。

完了条件は上記テストと既存テストが対象 Python で成功し、Core が ComfyUI プロセスなしで動作すること。テストコマンドは `python -m unittest discover -s tests -v`（ポータブル版のコマンドは README 参照）。この段階では ComfyUI 上で操作可能であることは完了条件に含めない。

## 8. 後続段階への引き継ぎ

1. **Nodes**：対象 ComfyUI の API を検証し、ユーザーデータパス、選択のワークフロー保存、複数入力、プレビューと実出力の一致を設計する。テンプレート更新時の選択移行も決める。
2. **Editor**：一覧・編集・保存・削除確認、プリセットの操作、API とエラー表示を実装する。
3. **Stability**：Live 更新時のキャッシュ無効化、Snapshot、インポート衝突の確認、バックアップと破損復旧を実装・検証する。

# Stability フェーズ設計案

作成日：2026-11-13  
状態：レビュー用提案。未実装。  
対象：現行の単一ユーザー環境と schema_version 1 のテンプレート。

## 目的と範囲

テンプレートを安全に移行でき、保存済みデータの破損や編集の競合に気づき、復旧できるようにする。その後、ワークフローの再現性を選択できるようにする。既存のノード種別・出力順・Live ワークフロー・テンプレート／ブロック／プリセット ID を維持する。複数ユーザー対応、クラウド同期、複雑なタグ構文の意味解析は対象外。

## 現状と課題

- 保存はユーザーディレクトリのテンプレート単位の JSON。スキーマ、ID、ファイル種別を検証し、一時ファイルから置換する。新規作成は既存ファイルを上書きしない。
- 一覧は各 JSON を読み込むため、1 件の破損でも一覧全体が失敗する。読み込みや保存に失敗すると API は汎用エラーを返す。編集画面の下書きはメモリ上にあり、失敗時には残るが、画面を閉じると失われる。
- 保存と削除は読み込み時点の版を確認しない。複数画面や外部編集との競合で後の操作が先の変更を消し得る。削除には確認があるが復元機能はない。
- ノード状態 v1 はテンプレート ID と選択を保存し、実行・プレビュー時に現行 JSON を読む。テンプレートノードは毎回再実行される。ブラウザー側で選択を調整できるが、実行側はブロック不一致を明示的に拒否する。
- JSON の重複キーは `parse_template` で拒否する一方、通常の API の `request.json()` はパース済みオブジェクトを扱う。インポートは生の JSON をサーバーで検証する必要がある。

## 方針の比較

1. **移行機能を先に追加し、その後に復旧・競合・Snapshot を段階導入する（推奨）**。既存の安全な新規作成を活用でき、早期に持ち出し手段ができる。上書き取り込みは競合検出と復旧が整うまで提供しない。
2. **バックアップ・競合検出を先に完成してから移行機能を追加する**。上書きを含む移行を設計しやすいが、持ち出し機能の提供が遅れる。
3. **全機能を一括実装する**。機能間の一貫性を一度に設計できるが、状態形式や復旧の変更を同時に検証する負担が大きい。

以下は 1 を採用した場合の提案であり、優先順位や仕様はレビューで変更できる。

## 第1段階：インポート／エクスポート

- エディターで単一の保存済みテンプレートを JSON としてダウンロードし、単一 JSON ファイルを取り込む。エクスポートはサーバーの保存済み版を対象とし、未保存の下書きとは区別して表示する。保存失敗や未保存の編集を暗黙に含めない。
- インポートはファイル内容を生テキストとしてサーバーに渡し、`parse_template` による重複キー検出と既存のスキーマ検証を経て作成する。取り込み元ファイル名を保存先パスとして使わない。サーバー受信時にバイト数を制限し、生バイトを厳格な UTF-8 として検証する。無効な UTF-8、JSON、スキーマ、未対応バージョンへのエラーを設ける。上限値は実装時に既存運用を確認して決める。
- 元の ID が空いていればそのまま保存する。衝突した場合は既存ファイルを変更せず、キャンセルまたは新しいテンプレート ID で別コピーを作成する。ユーザーの確認後もサーバーの create を再実行し、競合を再検出する。ブロック・プリセット ID は変更しない。大文字小文字を区別しないファイルシステム上の衝突も拒否する。
- 上書き取り込みはこの段階では提供しない。既存の Live ワークフローは同じ ID を参照するため、新 ID のコピーには自動で切り替わらないと表示する。取り込み・画面切り替えで未保存の下書きを捨てる場合は既存の確認を使う。
- エクスポート・インポート API と画面操作は既存の単一ユーザー制限を通し、無効データや書き込み失敗時に既存ファイルを変更しない。現在のフロントエンド request ヘルパーは JSON 専用なので、ダウンロードの応答形式と取得経路を別途設計する。API の形やレスポンスの詳細は実装計画で確定する。

## 第2段階：復旧と競合

- 一覧に正常な項目と問題のあるファイルの識別情報を分けて返し、問題を明示しながら正常なテンプレートを利用できるようにする。破損した内容を空テンプレートに置き換えたり、自動修復したりしない。既存 API 利用側の互換性を確認して導入する。パスやエラー詳細の露出は最小限とし、詳細はサーバーログで確認できるようにする。
- 更新・削除の前に現在の内容の復旧用コピーを同じユーザーデータ領域に作り、作成に失敗したら元ファイルを変更しない。バックアップの命名、保持数、復元 UI、ディスク容量不足時の扱いは実装前に具体化する。復元するバックアップは検証し、現行データを無確認で置き換えない。現行ファイルが破損して読み込めない場合はその生データを保全し、欠損・破損のそれぞれについて状態の確認と明示的な復元条件を設ける。復元操作の間の変更も検出対象とする。バックアップは通常の `*.json` 一覧に混ぜない。
- 読み込み時の内容に基づく版トークンを返し、保存・削除時に提示させる。版が変わった、消えた、破損した場合は操作を拒否し、下書きを維持したまま再読み込みや別 ID 保存への道を示す。取り込みの上書き対応を検討する場合も同じ保護を使う。
- チェック後の置換までをアプリ内の操作について直列化する。外部ツールはそのロックに参加しないため、通常のファイルシステムだけで外部編集との完全な原子的競合防止を保証しない。外部変更の検出範囲と残る競合窓を実装時に検証し、利用者に説明する。

## 第3段階：Snapshot

- 明示的に Snapshot を作成したとき、検証済みテンプレート全体と選択状態をワークフロー内に保存する。以後の実行とプレビューは保存された内容を共通の prompt builder に渡し、外部 JSON の変更・削除に依存しない。明示的な更新以外で Snapshot を変更しない。
- v1 状態は既存どおり Live と解釈する。Snapshot は別バージョンの状態形式を定義して厳格に検証し、未知バージョンは明示的に拒否する。ノード種別と出力順は維持する。古いプラグインに Snapshot を含むワークフローを戻す互換性は保証せず、明示する。
- Live → Snapshot は現在のテンプレートと選択の検証が成功した場合のみ可能。Snapshot → Live は現在のライブラリ版との差異と欠損を示し、ユーザーの操作で切り替える。選択の照合規則、更新操作、データ容量と機密性の注意、UI 表示はこの段階の詳細設計で確定する。
- Snapshot の画面初期化はライブラリ一覧・対象ファイルの取得に依存させず、一覧取得失敗や対象欠損時も保存内容から表示・選択操作・実行・プレビューできるようにする。Snapshot でもプレビューとノード実行が同じデータ・選択を使うことを確認する。Live の再実行方式は維持する。

## 共通の検証と完了条件

- 各段階で Python と JavaScript の既存チェックを実行し、追加した失敗経路をテストする。特に不正 JSON・重複キー・ID 衝突・競合・破損・書き込み失敗時の元データ保持を確認する。
- インポート／エクスポートは日本語や複雑なタグ文字列の往復、同 ID の衝突、途中の失敗、未保存下書きを確認する。復旧はバックアップ失敗・復元時の競合・破損ファイル混在を確認する。Snapshot は v1 Live 互換、ファイル変更／削除、状態不正、プレビューと実出力の一致を確認する。
- 対象 ComfyUI でノード作成、エディター、ワークフロー保存／再読込、プレビュー、実行キャッシュ、エラー表示を手動確認する。環境が利用できない場合は未確認として報告する。稼働中のインストールやユーザーデータを無断で変更しない。
- ユーザー向けの挙動が変わる各段階で README の日英両方を更新する。未実装の機能は利用可能と記載しない。
